## ADR-001　逐字归档与原文锚点（方案 A）

**状态：已落地（代码就绪，待重启端到端验证）**

### 背景
完整对话记忆存在三处但未打通：旧 livingmemory 库（已停用、停在 11-10）、滑动窗口快照（截断即丢）、memory_v2 的结构化摘要（非逐字）。结果是窗口内约 50 轮有原话，窗口外只剩摘要，11-10 后逐字断档。

### 决策
采用轻量「逐字归档 + 原文锚点 + 按需检索」：
- 每轮 user/assistant 原文持续写入本地 SQLite（WAL + FTS5 + 中文二元组）；
- `EventItem` 增加 `transcript_turn_id` 指向同轮逐字；
- 提供 `recall_transcript` 工具，仅在需要原话时按需检索，不常驻前缀；
- 历史 1171 条一次性迁移，按稳定 id 幂等。

### 理由
- 不把逐字塞进固定前缀，故**不降低前缀缓存命中率**；
- 本地操作、零 API 调用，不增加运行成本；
- 「只存摘要 + 按需取原话」兼顾 token 经济与可追溯。

### 影响
新增 `modules/transcript_store.py` 与迁移/测试工具；`*.db` 不入版本库。曾考虑的「重写窗口/全量常驻」方案因成本与缓存风险被否。

## ADR-002　前缀缓存修复采用分段丢弃（dequeue 1→10）

**状态：已落地并实测验证**

### 背景
滑动窗口打满后，`dequeue_context_length=1` 导致每超限只丢 1 轮，前缀逐轮位移，跨轮固定约 40% 命中，仅命中 system+工具 schema 固定前缀（约 17.4k），约 20k 历史每轮全价重算。

### 决策
将 `dequeue_context_length` 改为 10：超限时一次丢 10 轮、保留 51 轮，其后 9 轮前缀保持不动。

### 理由与实测
- 稳定态缓存命中率升至 **98.2%–98.8%**；
- 主对话单次等效输入 29,171 → 8,127 token，**降 72.1%**；10 轮平均降约 67%；
- 代价是窗口在 51–60 轮间循环，平均保留 55.5 轮，仍满足对话需要。

### 影响
仅改一个配置键，全量 JSON diff 无其他变化，保留 UTF-8 BOM，改动前已备份。

## ADR-003　通道选择（暂不切换，先量化）

**状态：待决策**

### 背景
同口径月成本：百炼 PAI 约 127.6 元，DeepSeek 官方按真实峰谷映射约 26–28 元，渠道倍数约 4.8，切换可省约 79%。

### 决策
暂不切换，先完成 OpenAI 兼容端点、缓存字段名与 usage 记录链的验证；并优先拆分占现成本约 60% 的后台小请求成分，避免在未测量前盲目动作。

### 原则
先测量、后优化；不以牺牲响应方式或污染编造复发率观测面为代价换成本。
